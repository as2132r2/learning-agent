# LangChain Day27：生产监控、SLO、告警与事故恢复

## 一、今天解决的问题

前面的系统已经具备 RAG、缓存、评估、反馈和灰度发布能力。Day27 进一步回答生产环境中的问题：

```text
系统现在是否健康？
→ 用户实际得到的服务质量是否达标？
→ 错误预算是否正在快速耗尽？
→ 同一个故障是否会重复通知？
→ 故障由谁处理、经历了哪些状态？
→ 新版本异常时能否安全回滚？
→ 运维人员如何从一个页面观察全局？
```

核心闭环：

```text
请求事件 → SLI → SLO → 错误预算 → 燃烧率
→ 告警 → 事故 → 自动回滚 → 恢复验证 → 可视化与审计
```

## 二、固定七步回顾

### 第 1 步：SLI、SLO 与错误预算

文件：`day27/python/day27_slo_basic.py`

- SLI 是实际测量值，例如可用率、质量通过率、P95 延迟。
- SLO 是内部服务目标，例如可用率至少 99%。
- SLA 通常是对客户承诺的合同级协议，不应与 SLO 混用。

计算关系：

```text
可用率 = 成功请求数 / 总请求数
质量通过率 = 质量通过请求数 / 总请求数
允许错误率 = 1 - SLO
实际错误率 = 1 - SLI
错误预算消耗比例 = 实际错误率 / 允许错误率
```

99% 可用率意味着 100 次请求允许约 1 次失败。实际失败 3 次，预算消耗就是 300%。

延迟使用 P95 而不是平均值，是为了观察绝大多数用户体验，同时避免少量极端值完全支配指标。

### 第 2 步：滚动窗口与燃烧率

文件：`day27/python/day27_burn_rate.py`

燃烧率定义：

```text
burn rate = 当前实际错误率 / SLO允许错误率
```

- `1x`：按整个 SLO 周期刚好耗尽预算；
- `20x`：以正常速度的 20 倍消耗预算；
- `<1x`：消耗速度在目标范围内。

多窗口判断不是只看某一分钟，也不是只看长期平均：

```text
5m + 1h 同时很高 → 快速燃烧，立即 page
30m + 6h 持续偏高 → 慢速燃烧，创建 warning
```

短窗口发现得快但噪声大；长窗口稳定但反应慢。两者同时成立可以降低误报。

### 第 3 步：告警去重、抑制和恢复

文件：`day27/python/day27_alert_manager.py`

告警不是每次检查失败都发一条新消息，而是维护一个有状态对象：

```text
normal → open → duplicate/suppressed → resolved
```

重要机制：

- `alert_key` 唯一标识同一种故障；
- 已打开的相同告警只增加 occurrence，不重复轰炸；
- 维护窗口中记录事件，但抑制外部通知；
- 指标恢复时发送一次恢复通知；
- `alert_events` 保存不可丢失的审计历史。

### 第 4 步：事故状态机和时间线

文件：`day27/python/day27_incident_lifecycle.py`

事故状态：

```text
detected → acknowledged → investigating → mitigated → resolved
```

状态机明确允许的转移，防止从 `detected` 直接跳到不合理状态。

版本号用于乐观锁：

```sql
UPDATE incidents
SET status = ?, version = version + 1
WHERE incident_id = ? AND version = ?
```

若两名运维人员同时编辑，后提交的旧版本更新会失败，避免静默覆盖。

`incident_timeline` 保存每次状态变化、操作者、说明和时间，形成完整事故时间线。

### 第 5 步：自动回滚和恢复验证

文件：`day27/python/day27_auto_rollback.py`

发布状态包含：

- 当前活跃版本；
- last-known-good 版本；
- protection 状态；
- 冷却截止时间；
- 状态版本号。

回滚流程：

```text
page级事故
→ 检查是否已执行过
→ 候选版本 quarantined
→ control/last-known-good 激活
→ 写入 rollback_actions
→ 进入 cooldown
→ 连续健康探针通过
→ 解除保护状态
```

幂等性保证同一事故重复触发时不会重复回滚。冷却时间防止刚恢复就立即重新发布，形成版本来回抖动。

### 第 6 步：生产运维 Web 控制台

最终文件：

- `day27/python/day27_final_ops_dashboard.py`
- `day27/html/day27_final.html`
- `day27/javascript/day27_final.js`
- `day27/css/day27_final.css`

服务端每 15 秒执行一次监控循环，前端每 5 秒读取一次状态。两者职责不同：

```text
后台监控：产生和更新事实
前端轮询：只展示服务器已经确认的事实
```

接口：

```text
GET  /health             健康检查
GET  /api/overview       当前监控全景
POST /api/monitor/run    手动立即执行一次监控
GET  /                   控制台页面
```

## 三、重要概念之间的关系

| 概念 | 回答的问题 | 是否产生动作 |
|---|---|---|
| SLI | 实际表现是多少 | 否 |
| SLO | 目标是多少 | 否 |
| 错误预算 | 允许失败多少 | 否 |
| 燃烧率 | 预算消耗有多快 | 否 |
| 告警 | 是否需要通知人或系统 | 通知 |
| 事故 | 如何组织故障处理过程 | 状态管理 |
| 回滚 | 如何降低故障影响 | 修改发布状态 |
| 审计日志 | 谁在何时做了什么 | 保存证据 |

不能把“指标异常”直接等同于“每次都执行回滚”。中间必须经过多窗口判断、告警状态、事故身份和幂等检查。

## 四、数据库中的事实层

Day27 共用 `day27_operations.db`，主要保存：

```text
request_events               原始请求事件
burn_rate_snapshots          燃烧率快照
alert_states                 告警当前状态
alert_events                 告警审计事件
maintenance_windows          维护窗口
incidents                    事故当前状态
incident_timeline            事故不可变时间线
service_release_state        服务当前发布状态
release_versions             各版本状态
rollback_actions             回滚操作记录
recovery_probes              恢复探针结果
```

“当前状态表”和“历史事件表”同时存在：前者便于快速读取当前事实，后者便于审计和复盘。

## 五、今天最重要的设计原则

1. 监控以用户结果为中心，而不只看服务器是否存活。
2. 告警使用多窗口，兼顾速度和稳定性。
3. 重复异常不等于重复通知和重复回滚。
4. 所有高风险动作必须幂等并可审计。
5. 自动恢复不等于候选版本自动重新上线。
6. 前端不是事实来源，数据库和后端状态机才是。
7. SLO 阈值必须来自业务目标和真实数据，不能永久照搬教学数字。
